# Contributing Guide

## Cloning the Project

```bash
git clone https://github.com/GooGuTeam/g0v0-server.git
```

Additionally, you will need to:

- Clone the spectator server into the g0v0-server directory:

```bash
git clone https://github.com/GooGuTeam/osu-server-spectator.git spectator-server
```

- Clone the performance server into the g0v0-server directory:

```bash
git clone https://github.com/GooGuTeam/osu-performance-server.git performance-server
```

- Download and place custom ruleset DLLs into the `rulesets/` directory (if needed).

## Development Environment

To ensure a consistent development environment, we strongly recommend using the provided Dev Container. This sets up a containerized environment with all necessary tools and dependencies pre-installed.

1. Install [Docker](https://www.docker.com/products/docker-desktop/).
2. In Visual Studio Code, install the [Dev Containers extension](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-containers).
3. Open the project in VS Code. When prompted, click "Reopen in Container" to launch the development container.

## Project Configuration

Modify the `.env` configuration (refer to the [wiki](https://github.com/GooGuTeam/g0v0-server/wiki/Configuration)), generate, and fill in the JWT secret key.

If running in the Dev Container, set `MYSQL_HOST` to `mysql` and `REDIS_URL` to `redis://redis/0`.

## Starting the Project

The `.devcontainer` folder provides a startup script `start-dev.sh`, which loads environment variables from `.env` and simultaneously starts g0v0-server (port `8000`) and spectator-server (port `8006`).

The Dev Container provides NGINX for reverse proxying, with the external access port being `8080`.

If your server does not have HTTPS configured, you can specify the environment variable `OSU_INSECURE_REQUESTS=1` when launching osu! to disable SSL verification, or apply the diff provided in the [osu!lazer wiki](https://github.com/ppy/osu/wiki/Testing-web-server-full-stack-with-osu!#basics).

Alternatively, use the following commands to start manually:

```bash
# g0v0-server
uv run uvicorn main:app --host 0.0.0.0 --port 8000 --reload
# spectator-server
cd spectator-server
dotnet run --project osu.Server.Spectator --urls "http://0.0.0.0:8086"
```

## Development Guidelines

### Project Structure

Below is an overview of the main directory and file structure:

- `main.py`: Main entry point for the FastAPI application, responsible for initializing and starting the server.
- `pyproject.toml`: Project configuration file used to manage dependencies (uv), code formatting (Ruff), and type checking (Pyright).
- `alembic.ini`: Configuration file for the Alembic database migration tool.
- `app/`: Contains all core application code.
  - `router/`: Contains all API endpoint definitions, organized by API version and functionality.
  - `service/`: Contains core business logic, such as user ranking calculations and daily challenge processing.
  - `database/`: Defines database models (SQLModel) and session management.
  - `models/`: Defines non-database models and other data schemas.
  - `tasks/`: Contains background tasks scheduled by APScheduler as well as startup/shutdown tasks.
  - `dependencies/`: Manages FastAPI dependency injection.
  - `achievements/`: Contains achievement-related logic.
  - `storage/`: Storage service implementations.
  - `fetcher/`: Modules for fetching data from external services (e.g., the official osu! website).
  - `middleware/`: Defines middleware, such as session verification.
  - `helpers/`: Contains helper functions and utility classes.
  - `config.py`: Application configuration managed via pydantic-settings.
  - `calculator.py`: Contains calculation logic, such as pp and levels.
  - `log.py`: Logging module providing a unified logging interface.
  - `const.py`: Defines constants.
  - `path.py`: Defines constants used across files.
- `migrations/`: Contains database migration scripts generated by Alembic.
- `static/`: Contains static files, such as `mods.json`.

### Database Model Definition

All database models are defined in `app.database` and exported in `__init__.py`.

This project uses an "on-demand return" design pattern following the `Dict` - `Model` - `Table` structure. For detailed design rationale, refer to [this article](https://blog.mxgame.top/2025/11/22/An-On-Demand-Design-Within-SQLModel/).

#### Basic Structure

1. **Dict**: Defines the dictionary structure after model transformation, used for type checking. Must be defined before Model.
2. **Model**: Inherits from `DatabaseModel[Dict]`, defining fields and computed properties.
3. **Table**: Inherits from `Model`, defining the database table structure.

```python
from typing import TypedDict, NotRequired
from app.database._base import DatabaseModel, OnDemand, included, ondemand
from sqlmodel import Field

# 1. Define Dict
class UserDict(TypedDict):
    id: int
    username: str
    email: NotRequired[str]  # Optional field
    followers_count: int     # Computed property

# 2. Define Model
class UserModel(DatabaseModel[UserDict]):
    id: int = Field(primary_key=True)
    username: str
    email: OnDemand[str]     # Mark optional field using OnDemand

    # Standard computed property (always returned)
    @included
    @staticmethod
    async def followers_count(session: AsyncSession, instance: "User") -> int:
        return await session.scalar(select(func.count()).where(Follower.followed_id == instance.id))
    
    # Optional computed property (returned only when specified in includes)
    @ondemand
    @staticmethod
    async def some_optional_property(session: AsyncSession, instance: "User") -> str:
        ...

# 3. Define Table
class User(UserModel, table=True):
    password: str            # Field that exists only in the database
    ...
```

#### Field Types

- **Standard Attributes**: Defined directly on the Model; always returned.
- **Optional Attributes**: Marked with `OnDemand[T]`; returned only when specified in `includes`.
- **Standard Computed Properties**: Static methods decorated with `@included`; always returned.
- **Optional Computed Properties**: Static methods decorated with `@ondemand`; returned only when specified in `includes`.

#### Usage

**Transforming Models**:

Use the `Model.transform` method to convert a database instance into a dictionary:

```python
user = await session.get(User, 1)
user_dict = await UserModel.transform(
    user,
    includes=["email"],  # Specify optional fields to return
    some_context="foo-bar",  # Pass additional parameters if computed properties require context
    session=session      # Optionally pass your own session
)
```

**API Documentation**:

In FastAPI routes, use `Model.generate_typeddict` to generate accurate response documentation:

```python
@router.get("/users/{id}", response_model=UserModel.generate_typeddict(includes=("email",)))
async def get_user(id: int) -> dict:
    ...
    return await UserModel.transform(user, includes=["email"])
```

Database module names should match the table name, except where multiple models are defined.

If you need a Session, use `with_db` provided by `app.dependencies.database`, and remember to manually call `COMMIT`.

```python
from app.dependencies.database import with_db

async with with_db() as session:
    ...
```

### Redis

Choose the appropriate Redis client based on your intended use case. If your use case is complex or geared toward a larger subsystem, consider creating a dedicated Redis connection.

- `redis_client` (db0): Standard usage for strings, hashes, and other general data.
- `redis_message_client` (db1): Used for message caching, storing chat logs, etc.
- `redis_binary_client` (db2): Used for binary data storage, such as audio files.
- `redis_rate_limit_client` (db3): Exclusively used by FastAPI-Limiter.

### API Router

All API routers are defined in `app.router`:

- `app/router/v2` contains all osu! v2 API implementations. **No additional endpoints not present in the original v2 API are allowed.**
- `app/router/notification` **contains all osu! v2 API chat, notification, and BanchoBot implementations. No additional endpoints not present in the original v2 API are allowed.**
- `app/router/v1` contains all osu! v1 API implementations. **No additional endpoints not present in the original v1 API are allowed.**
- `app/router/auth.py` contains account authentication and login APIs.
- `app/router/private` contains custom server APIs (g0v0 API) for use by other services.

Any router must satisfy:

- Use Annotated-style dependency injection.
- For existing dependency injections such as Database and Redis, use the implementations in `app.dependencies`.
- Include documentation.
- If the response requires asset proxying, use the `asset_proxy_response` decorator from `app.helpers.asset_proxy_helper`.
- If logging is needed, use the `log` function provided by `app.log` to obtain a logger instance.

#### Authentication

If the router can be used publicly (clients, frontends, OAuth applications), consider using `Security(get_current_user, scopes=["some_scope"])`, for example:

```python
from typing import Annotated
from fastapi import Security
from app.dependencies.user import get_current_user


@router.get("/some-api")
async def _(current_user: Annotated[User, Security(get_current_user, scopes=["public"])]):
    ...
```

For scope selection, refer to `scopes` under `oauth2_code` in [`app.dependencies.user`](./app/dependencies/user.py).

If the router is strictly for client and frontend usage, use the `ClientUser` dependency injection:

```python
from app.dependencies.user import ClientUser


@router.get("/some-api")
async def _(current_user: ClientUser):
    ...
```

Additionally, `get_current_user_and_token` and `get_client_user_and_token` variants are available to retrieve both the current user and token simultaneously.

### Service

All core business logic resides in `app.service`:

- Business logic should be implemented as classes.
- For logging, simply use `logger` from `app.log`. The server wraps service loggers.

### Scheduled Tasks / Startup Tasks / Shutdown Tasks

All are defined in `app.tasks`:

- All are exported in `__init__.py`.
- Startup and shutdown tasks are invoked in `main.py`'s `lifespan`.
- Scheduled tasks use APScheduler.

### Long-running Tasks

- If the task originates from an API router, use FastAPI's [`BackgroundTasks`](https://fastapi.tiangolo.com/tutorial/background-tasks).
- Otherwise, use `bg_tasks` from `app.utils`, which provides functionality similar to FastAPI's `BackgroundTasks`.

### Code Quality and Linting

Use `pre-commit` to enforce code quality standards before committing. This ensures all code passes `ruff` (for linting and formatting) and `pyright` (for type checking).

#### Setup

To set up `pre-commit`, run:

```bash
pre-commit install
```

This installs pre-commit hooks that run automatically on each commit. If any check fails, the commit will be aborted. You must fix reported issues and stage your changes before attempting to commit again.

pre-commit does not provide a hook for pyright; you must manually run `pyright` to check for type errors.

### Commit Message Guidelines

Follow the [AngularJS commit conventions](https://github.com/angular/angular.js/blob/master/DEVELOPERS.md#commit-message-format) when writing commit messages.

**Type** must be one of the following:

- **feat**: New feature
- **fix**: Bug fix
- **docs**: Documentation changes only
- **style**: Changes that do not affect the meaning of the code (whitespace, formatting, missing semi-colons, etc.)
- **refactor**: Code refactoring
- **perf**: Performance improvements
- **test**: Adding missing tests or correcting existing tests
- **chore**: Changes to build process or auxiliary tools and libraries (such as documentation generation)
- **ci**: CI configuration changes
- **deploy**: Deployment-related changes

**Scope** can be anything specifying the place of the commit change, e.g., `api`, `db`, `auth`, etc. Use `project` for repo-wide changes.

**Subject** contains a concise description of the change.

### Continuous Integration Checks

All commits should pass the following CI checks:

- Ruff Lint
- Pyright Lint
